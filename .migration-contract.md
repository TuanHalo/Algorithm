# 🧭 Migration Contract: Old Pages → 3D Story Pages

> This is the contract for moving every lesson and problem page from the old layout (separate visualizer, code block, approach cards and Archify flow) to **one 3D story** that goes **problem → idea → code → run → why**.
> Every migrated page must match this file. If this file and `.ai-contract.md` disagree about a migrated page, **this file wins**. Once migration is complete, fold these rules into `.ai-contract.md` and delete this file.

**Reference implementation:** `src/walkthroughs/problems/two-sum.ts` + `src/content/problems/two-sum.md` (official reference since Phase 1). Copy its patterns; don't invent new ones.

---

## 1. Why we are migrating

The current Two Sum page explains the same thing several times, in the wrong order:

| Content | Old page shows it in |
|---|---|
| The approach | approach cards + "My approach" text + walkthrough steps |
| The code | walkthrough code panel + "My solution" block |
| The step-by-step flow | 3D walkthrough + Archify "visual walkthrough" iframe |
| Edge cases | AI-feedback list + trace presets |

The new page says each thing **once**, inside a story where the code grows from the idea.

## 3. The story: five chapters, always in this order

Each step sets `chapter`. The step rail groups its dots under chapter names.

| Chapter | Purpose | 3D scene | Code panel | Steps |
|---|---|---|---|---|
| `problem` | What we're given and what we must return | example input, target, expected output as a note | **signature only** (line 1) | 1–2 |
| `idea` | The obvious approach and why it isn't enough; the insight | brute-force arcs / naive scan, cost note | brute-force **snapshot** (if one exists), then back to the signature | 1–3 |
| `build` | Turn the insight into code, one idea at a time | each idea introduces its entity (e.g. the `seen` card appears with the "notebook" idea) | **code grows**: each step reveals the final-solution lines for that idea | 2–9 (≤ 3 new lines each) |
| `run` | Dry run on the example until the answer, **one decision per step** (see rules) | the full trace on the story input | **final code**, running lines highlighted, **inline values** | 3–10 (lessons: as many as the trace needs) |
| `why` | Complexity recap, then the **key decision** of this solution as the **last step** | final state + recap / pitfall note | final code, key lines | 2 (recap, then key decision) |

Rules:
- **8–14 steps** per problem story; lesson stories may go up to **48**, because their `run` chapter traces the whole algorithm. Long lesson stories build their `run` steps from the same function as the trace (`...traceX(INPUT)`), so story and trace can't drift apart; `build` steps reuse those scenes (`RUN[n].scene`).
- **`run`: one decision per step** (owner feedback, 2026-11-22). Never fold several actions into one step. Each of these gets its own step, so a reader can follow the loop without re-deriving it:
  - setting up the variables and the first loop check
  - computing the probe (`mid`, `pos`, the dividers, the next capacity…)
  - the comparison and what it means ("16 < 23, so the target is to the right")
  - the move it causes (`low = 5`), with what that rules out
  - a helper call's result (`can_ship(…, 7)`), and the decision taken on it
  - every recursive call and every pass of a sub-algorithm, **in the same detail** (owner feedback, 2026-11-22: merge sort's halves came back already sorted, quick sort hid its recursion, heap sort skipped the heap build, radix sort skipped the digit pass). Never show a call as a finished result the reader didn't watch being made
  - the return
  Loop turns after the first may combine the loop check with computing the probe. The trace (Try your own) follows the same granularity.
- **Explain every formula.** When a line computes something non-obvious (interpolation's `pos`, `mid = low + (high − low) // 2`), a story step says **where it comes from** (derivation or picture) before the run uses it.
- The **last step is always the key decision** in this solution (Two Sum: "check before store", the comment on line 7). The complexity recap comes right before it.
- `problem` must state the input, the output and one constraint that matters. Link to the full statement through the header button; don't copy it.
- `idea` must match the frontmatter `approaches`: the non-optimal approach is the brute force shown here, and the optimal one is what `build` constructs.

## 4. Code rules: idea → code

### 4.1 Single source of truth
- `code.source` in the walkthrough is **the** solution: the exact code submitted for problems, the reference implementation for lessons. It is not repeated anywhere else on the page.
- **One core function per lesson** (owner decision, 2026-11-24). When an old lesson's code has several functions, the story builds the lesson's core technique only. The other functions are dropped, and the problems they solve are named in the "When to use" table. Exceptions are possible when the title names two techniques (Prefix Sum & Difference Array builds both classes). Prefer a numeric version over a string one when both exist, so trace mode can run it.
- The component server-renders the final code as static text, so it works without JavaScript and has a **Copy** button.
- PEP 8, type hints, and comments that explain **why** (as in `.ai-contract.md`).

### 4.2 Code views per step
Every step has a `code` view. The view decides **what code is visible**; `lines` decides **what is highlighted**.

| View | Shows | Used in |
|---|---|---|
| `signature` | the final code up to its first `def` (imports included) + `...` | `problem` |
| `snapshot:<id>` | an extra code listing declared in `snapshots` (e.g. `brute`) | `idea` |
| `reveal` | only the final-code lines listed in `reveal`; gaps collapse to `...` at the right indentation | `build` |
| `final` | the whole final solution | `run`, `why` |

- `reveal` lists the **complete set** of visible final-code lines for that step (not a diff), so any step can be opened directly by its link. **Blank lines are never listed**: one shows automatically when the lines above and below it are both visible.
- The gutter always shows the **final-code line numbers** (or the snapshot's own numbers), with `⋮` for a collapsed gap, so "Line 5" in the narration matches what's on screen.
- In `build`, reveals only grow, and each step adds **at most 3 lines**. The final `build` step reveals everything.
- `lines` must be a subset of the visible lines. A step whose idea isn't in the code (brute force without a snapshot) uses `signature` and says so in the narration.
- Moving between views animates with **magic move**: kept tokens slide, new tokens fade in and glow for one step.

### 4.3 Linking the scene to the code
- An entity that represents a code variable sets `codeVar: '<identifier>'` (e.g. the array `nums`, the map `seen`, the pointer `idx`). **Variable-panel rows link automatically** by their `name` when it is an identifier (`target`, `complement`). Hovering either side highlights every matching token and the 3D entity.
- **Entity labels use the real identifiers from the code** (`nums`, `seen`, `idx`, `low`, `high`, `mid`); never paraphrase them.
- In `run`, steps provide `values`: per-line inline values shown as ghost comments after the line, e.g. `{ 4: 'complement = 6', 5: 'True' }`.

## 5. 3D style rules (what "same style" means)

### 5.1 Floor layout
Scenes are authored in floor coordinates (x right, y down) and projected to isometric 3D.

| Element | Position |
|---|---|
| Main array | `x: 0, y: 0`, at most **10 cells** in the story |
| Variables panel (`vars`, id `vals`) | `x: 0, y: 150` |
| Map / dict / set (`map`) | right of the array, `y: 0`, at `x = tableBesideArray(cells, maxRows)` from `layout.ts`: `max(380, arrayWidth + 110)`, plus 19 px for every row past the fourth (cards are centred, so a taller card rises toward the array) |
| Notes | open floor, at least ~100 px from arrays and tables; max **3 lines × ~40 chars** |
| Second array (rare) | `y: 300` |
| Several arrays (merge, counting sort) | stacked at `y: 0, 130, 260` (or `0, 130, 250`); the variables panel moves right of the top array, `x = tableBesideArray(cells, rows)`, `y: 0`; notes go below the last row |
| A value "in hand" (insertion sort's `key`) | a one-cell array in front of the row (`y: 84`) under the slot it will drop into; the variables panel moves right as above |
| Recursion tree (merge sort) | one row per depth (`y = depth × 120`), each call a block row at its slice's position, with extra space at every split; the variables panel right of the widest row, `y: 0` |
| Call stack (quick sort) | a `map` labelled `call stack`, right of the array (`tableBesideArray`), top frame `note` tone ("running"), the others `muted` ("waits on line 9") |
| Tree drawn from an array (heap) | one-cell arrays keyed by value identity, laid out in **screen space** (root on top, levels straight below, left of the array) and converted to floor coordinates, so it reads as a tree in 3D; `indexLabels: [k]` shows each node's slot; `link` edges parent → child |
| Per-value helper row (radix's digits) | a row under the array (`y: 100`) with the same `itemKeys`, so it slides with its values; further rows at `y: 210, 330` |
| DP table | **1D:** the table is an array at `x: 0` (inputs on top at `y: 0`, the table below at `y: 130`), arcs from the cells a value reads into the cell being written (`active`; reads `compare`, the winning read `found` + `flow`, the losing one dashed `miss`). **2D:** stacked arrays, one per row, `y: 130` apart (`100`–`105` when a header row sits on top; `90` was too cramped in 3D); the header (`text2`, `s`, `p`) runs above the columns and a row's own letter sits in a one-cell block in front of it. A rolled 1D `dp` row sits on the grid row it is filling and slides down, leaving a copy of its old values above it (unique paths, knapsack). Variables right of the top row (`tableBesideArray`), notes below the last row. When `2ⁿ` rows would be too tall (bitmask DP), draw the table transposed. The `idea` chapter writes the naive recursion's call counts into the table cells, repeats in `miss` |
| Graph (graph lessons) | `drawGraph` from `src/lib/walkthrough/graph.ts`: each vertex a one-cell array placed in **screen space** left of the tables (fixed layout per vertex count, flowing left to right from vertex 0) and converted to floor coordinates; each edge a `link` keyed by its input index (an undirected edge is two opposite links on one arc, so it reads double-headed; antiparallel directed pairs are rejected); weights as edge labels; per-vertex state (`d 3`, `tin/low`, `color 0`) as `indexLabels` under the block. Tables start at floor `x: 0` (`x: 110` when a column of rows would reach the graph); trace inputs are `n` plus parallel `from` / `to` / `weight` lists |
| Stack / queue / deque (stack-queue lessons) | the container is an array at `x: 0, y: 0` (stack: bottom → top left → right; queue / deque: front → back), `itemKeys` = push / arrival number so values fade in and out; a pin marks the end in use (`top`, or `front` / `back`). A queue or deque moves its array one cell right per front removal (`x = removed × PITCH`), so a dequeue removes one block and nothing appears to shift. Empty is one muted `—` cell (key `empty`, no index). A stack of **indices** (monotonic stack / queue) is an extra row under the input (`y: 130` or `260`), keyed by index, with `nums=<value>` as the sub-label. Min / max caches are helper rows (`y: 100, 210`) sharing the stack's `itemKeys`. A value just taken off an end is a one-cell array in front of its old slot (`y: 84`) |
| Linked list (singly linked list) | one one-cell array per node, id `node-<id>`, `itemKeys: [id]`, `showIndex: false`, standing in its own slot `x = id × 100` (nodes never move in memory); a muted `None` block after the last slot; every `next` is a link `next-<id>` that leaves the right face and enters the left one when it points forward; `head` / `curr` / `prev` / `slow` / `fast` are pointers on the node they hold; a node no live variable can reach is lifted out of the row (floor x − 60, y − 100: up and a little right on screen, clear of its neighbour's pins), muted, its arrow dashed |

### 5.2 Entity ids and naming
- Ids stay **stable across every step** of the story, so things animate instead of being redrawn.
- Id = code identifier where one exists (`nums`, `seen`, `idx`); the variables panel is always `vals`; the lookup link is always `look`. Entity ids allow only letters, digits and dashes, so `min_idx` becomes `min-idx` (its label and `codeVar` stay `min_idx`).
- **Values that move** (swaps, partitions, digit passes) pass `itemKeys` on their array: one stable key per value, such as its original index. The block then slides to its new slot instead of changing its number in place. Arrays that copy values (insertion sort's shift, counting sort's output) show Python's real state and skip `itemKeys`.
- **Show where the algorithm is.** Recursion shows which call is running and what it works on: merge sort draws the recursion tree (one row per depth, a `note`-tone band on the running call), quick sort puts `low` / `high` pointers and a band on the slice plus a `call stack` map. A data structure hiding in an array is drawn as that structure: heap sort draws the tree next to the array.
- Exception: a step that switches to a **different example input** (Two Sum's "Order matters" uses `[5, 1]`) gives that array a new id (`trap`) but keeps `codeVar: 'nums'`, so the old array fades out instead of appearing to mutate.

### 5.3 Tones (fixed meaning, never repurposed)

| Tone | Meaning | Limit |
|---|---|---|
| `active` | the element being processed now | **one** per step (plus its pointer and the table row it was just written to). Derived values like `complement` stay plain until a check gives them `miss` / `found` |
| `compare` | being compared / current search window | |
| `done` | already processed or stored | |
| `found` | the answer / successful match | only when there is a match |
| `miss` | failed check, wrong path, bug | |
| `muted` | ruled out / no longer relevant | |
| `note` | callout cards | |

The legend lists **only the tones the story uses**.

### 5.4 Links, metrics, narration
- **Links:** a lookup or read is a `link` labelled `"<x>? no"` on a miss, or `"<x> → <result>"` on a hit. `flow: true` (moving packet) **only on the success path**. Use `dashed` for misses.
- **Metrics:** 2–4 counters with camelCase keys. The **last metric is the result** (`answer` / `result`), shown as `—` until known.
- **Narration:**
  - At most 2 short paragraphs and 3 sentences each, in a friendly tone.
  - Steps that run code **name the line numbers** ("Line 5 asks…").
  - Only `**bold**` and `` `code` `` formatting.
- **`short`** (rail label): at most 14 characters.
- **`changes`**: one bullet per state change (`seen[3] = 0`, `low = 5`).

### 5.5 Try your own (trace mode)
- Required for every lesson, and for every problem whose input fits on the stage.
- The trace uses **the same scene builder** as the story, so both modes look identical. Every trace step is chapter `run` with `{ view: 'final', lines }` and should provide `values` (the build checks the chapter and view).
- **At least 3 presets**: the platform's example, plus **every edge case** from the old AI feedback (duplicates, negatives, empty / no answer…).
- `maxItems` ≤ 10 (6 for `O(n²)` sorts, whose one-decision-per-step traces grow fast). Goals ("You'll learn") are hidden in this mode.
- Inputs accept whole numbers unless the input sets `decimals: true` (bucket sort's floats). Validate any narrower range in `run` and throw a friendly message (e.g. counting sort's "0 to 9").

## 6. Data format changes (schema v2)

These additions to `src/lib/walkthrough/types.ts` (and `schema.ts`) are built in **Phase 0**. Existing fields stay.

```ts
type ChapterId = 'problem' | 'idea' | 'build' | 'run' | 'why';

type CodeView =
  | { readonly view: 'signature'; readonly lines?: readonly number[] }
  | { readonly view: 'snapshot'; readonly id: string; readonly lines?: readonly number[] }
  | { readonly view: 'reveal'; readonly reveal: readonly number[]; readonly lines?: readonly number[] }
  | { readonly view: 'final'; readonly lines?: readonly number[] };

interface Step {
  // existing: short, title, body, metrics, changes, scene
  readonly chapter: ChapterId;
  readonly code: CodeView;                                      // replaces `code?: number | number[]`
  readonly values?: Readonly<Record<number, string>>;           // run chapter: inline values per final-code line
}

interface Walkthrough {
  // existing fields…
  readonly snapshots?: Readonly<Record<string, string>>;        // e.g. { brute: 'def two_sum(...)…' }
}

// Entities that stand for a code variable:
interface ArrayEntity /* MapEntity, VarsEntity, PointerEntity */ {
  readonly codeVar?: string;
}
```

New validation rules (the build fails when they are broken):
- Chapters appear in order and none are skipped (`idea` may be a single step).
- `build` reveals only grow, each step adds ≤ 3 lines, and the last `build` step reveals all lines.
- `lines` ⊆ visible lines; `values` keys are visible lines; `snapshot` ids exist.
- `codeVar` matches an identifier that appears in the visible code at least once in the story.
- The story has 8–14 steps (24 for lessons) and the last step is in chapter `why`.

**Rendering:** the code panel uses `@shikijs/magic-move` (pinned `4.6.0`).
- Layout: the narration sits **above a full-width code panel**, so inline values have room after each line.
- Files: `code-view.ts` (views → rows, shared), `code-frames.ts` (build-time precompute, server only), `code-panel.ts` (browser: renderer, gutter, highlight bars, values, Copy).
- Token steps are **precomputed at build time** with the site's Shiki 4 highlighter.
- Tokens are split on identifier boundaries and tagged `wt-var--<name>` for `codeVar` linking.
- The browser loads only the ~12 KB `MagicMoveRenderer`.
- This was checked in a spike: 5 Two Sum versions take 61 ms to precompute and 18 KB serialized, kept tokens slide correctly, and all 4 `seen` tokens can be tagged.

**Frontmatter:**

| Field | Change |
|---|---|
| problems `diagram` | removed |
| problems `approaches` | **kept**: the problem list page and header use it; the story's `idea` chapter must match it |
| lessons `visualizer` | removed in Phase 4 (after all lessons migrate) |
| lessons `diagram` | kept only for big-picture diagrams (§2.2) |
| lessons and problems `verified` | **new**, optional `"YYYY-MM-DD"`: set only by the owner's review (§10); drives the Verified badge |

## 9. Per-page checklist (definition of done)

**Content**
- [ ] The story has all five chapters in order, 8–14 steps (lessons ≤ 48), and the last step is the key decision.
- [ ] `run` takes **one decision per step** (setup, probe, compare, move, helper result, return), and the trace does the same.
- [ ] Every non-obvious formula is explained before the run uses it.
- [ ] `code.source` matches the old solution exactly (problems) or the reviewed reference implementation (lessons).
- [ ] Every step has a `code` view. `build` reveals grow by ≤ 3 lines per step and end with the full solution.
- [ ] Narration names line numbers in `build` / `run`. Labels and `codeVar` use real identifiers.
- [ ] `run` steps have `values` for the lines they highlight.
- [ ] Trace mode works with ≥ 3 presets covering every old edge case.
- [ ] Goals ("You'll learn") point at the right steps.

**Page**
- [ ] Removed sections are gone from the markdown (§2). AI feedback (problems) or the reference card (lessons) remains.
- [ ] Frontmatter is updated (§6). Obsolete diagram / visualizer files for this page are deleted.
- [ ] No content is said twice on the page.

**Style (§5)**
- [ ] Layout positions, stable ids, tone meanings, one `active` per step, legend matches the tones used.
- [ ] Notes and tables don't overlap blocks or each other in **any** step.

**Verification**
- [ ] `pnpm check` and `pnpm build` pass (the build runs walkthrough validation).
- [ ] In the browser (`pnpm dev` → `/Algorithm/...`): step through every story step, run every trace preset, and check at desktop width and at 375 px (no horizontal scroll).
- [ ] Back / Next stay in place on every step. The highlighted lines match the "Lines …" chip.

Passing this checklist makes a page **Built**. Only the owner's review (§10) makes it **Verified**.

## 10. Owner verification

The owner walks through every migrated lesson and problem in the browser. A page is **Verified** only after that review; the checklist above and a merged PR are not enough. Feedback from a review becomes a rule in this contract (as §3's "one decision per step" did), so later pages get it right first time.

**Statuses:**
- **Built**: passes §9, waiting for the owner.
- **Changes requested**: the owner reviewed it; the note says what to fix.
- **Rebuilt**: the requested changes are done, waiting for another review.
- **Verified** ✅: reviewed and accepted by the owner. Change it only for a reason the owner agrees to.

Update the row in the same change that builds or fixes the page.
