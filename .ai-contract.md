# 🤖 AI Contract — Algorithm Hub

> This file defines the rules and standards that any AI assistant (Antigravity, Copilot, etc.)
> **must follow** when contributing to this repository. Read this file before making any changes.

---

## 📌 Core Principles

1. **Friendly language** — Write like explaining to a friend, not a textbook. No academic jargon.
2. **Visuals over text** — Prefer diagrams, tables, badges, and interactive visualizations over long paragraphs.
3. **Consistency** — Every page, component, and diagram follows the established templates and design system.
4. **Interactive first** — Every algorithm lesson should include an interactive step-by-step walkthrough (new work) or visualizer (legacy).

## 📚 Algorithm Lesson Format (`src/content/learn/**/*.md`)

### Required Frontmatter

```yaml
---
title: "Algorithm Name"
topic: "topic-slug"        # sorting, searching, graph, etc.
order: 1                   # Display order within topic
difficulty: "beginner"     # beginner | intermediate | advanced
timeComplexity: "O(n²)"
spaceComplexity: "O(1)"
visualizer: "/visualizers/topic/algo-name.html"  # optional
diagram: "/diagrams/topic/algo-name-flow.html"   # optional
tags: ["tag1", "tag2"]
---
```

### Required Sections (in this order)

1. **🎯 What is [Algorithm]?** — 1-2 sentences. Use a real-life metaphor or analogy.
2. **🧠 Core Idea** — One-line summary in a blockquote. Example: `> Compare neighbors → Swap if wrong order → Repeat`
3. **🐍 Python Code** — Clean, commented implementation. PEP 8 compliant with type hints.
4. **⏱️ Complexity** — Table with Best / Average / Worst for both Time and Space.
5. **⚡ When to Use** — Two lines: ✅ Use when... / ❌ Avoid when...

> Note: The interactive visualizer (`visualizer:`) and Archify diagram (`diagram:`) declared in frontmatter are automatically rendered by `src/pages/learn/[topic]/[slug].astro` — do not leave empty HTML placeholder comments in Markdown.

### Writing Rules

- Maximum 2 sentences per explanation point
- Use emoji section headers (🎯, 🧠, 🐍, ⏱️, ⚡)
- Use tables instead of bullet lists for comparisons
- Code comments should explain **why**, not **what**
- Keep code under 30 lines (prefer concise implementations)

## 📝 Problem Solution Format (`src/content/problems/*.md`)

Every problem is a **3D story page** (`.migration-contract.md` §2.1). The page is built from two files, and each thing is said once:

| File | Holds |
|---|---|
| `src/walkthroughs/problems/<slug>.ts` | the problem, the idea, the submitted code (`code.source`), the dry run, the key decision, and the edge cases as trace presets |
| `src/content/problems/<slug>.md` | frontmatter + **AI feedback only** |

Copy `two-sum.ts` / `two-sum.md` as the template.

### Required Frontmatter

```yaml
---
title: "Problem Name"
platform: "leetcode"       # leetcode | hackerrank | codeforces | other
problemUrl: "https://..."
difficulty: "easy"         # easy | medium | hard
topics: ["hashing", "array"]
dateCompleted: "2024-01-15"
timeComplexity: "O(n)"
spaceComplexity: "O(n)"
approaches:                # optimal one → header + "Uses:" chips; non-optimal one → the story's `idea` chapter
  - name: "Hash Map (One Pass)"
    timeComplexity: "O(n)"
    spaceComplexity: "O(n)"
    isOptimal: true
    tags:
      - { label: "Hash Map", topic: "hashing", slug: "hash-map" }
---
```

### Markdown body: AI feedback only

`## AI feedback` with three subsections:
- **Strengths**: what the solution does well (2–4 bullets).
- **Improvements**: what could be better (1–4 bullets).
- **Alternative approaches**: approaches the story does **not** show (the brute force is already the story's `idea` chapter).

Don't write `## Problem`, `## My approach`, `## My solution` or `### Edge cases`: the story covers them (edge cases become trace presets). There is no `diagram` field for problems.

### Feedback Guidelines

When providing AI feedback on user's code:
- Be **encouraging first** — always start with genuine strengths
- Be **specific** — don't say "could be better", say exactly what and how
- Suggest **Pythonic** improvements (list comprehensions, built-ins, etc.)
- Mention **time/space tradeoffs** when suggesting alternatives
- Keep tone **friendly and supportive** — this is a learning journal, not a code review

## 🎬 Interactive Visualizer Rules

### Architecture

- All visualizers are **self-contained HTML files** in `visualizers/<topic>/`
- Use the shared engine: `visualizers/shared/visualizer-base.js`
- Use Claymorphism styles: `visualizers/shared/clay-visualizer.css`

### Required Features

Every visualizer must have:
1. **Input field** — User can enter custom data (e.g., array, graph)
2. **Step recording** — Algorithm records every comparison, swap, or operation
3. **Playback controls** — Play, Pause, Step Forward, Step Back, Speed slider
4. **Visual state** — Animated representation (bars, nodes, etc.)
5. **Code highlight** — Show the Python code alongside, highlight current line

### Styling

- Use Claymorphism design tokens (match the main site look)
- Pastel topic colors for highlighting active/compared elements
- Smooth CSS transitions (200-400ms)
- Responsive layout (works at 320px–1920px)

## 🎞️ Walkthrough Rules (step-by-step animated scenes)

> **Migration in progress:** pages are moving to a single 3D story (problem → idea → build → run → why). For any page being migrated or already migrated, **`.migration-contract.md` overrides this file** (page anatomy, story chapters, code views, 3D style).

A walkthrough is a narrated, step-by-step animation that renders inline on the lesson or problem page. It is the preferred way to show **how an algorithm or solution executes**.

### Where files live

| What | Path |
|------|------|
| Problem walkthrough | `src/walkthroughs/problems/<problem-slug>.ts` |
| Lesson walkthrough | `src/walkthroughs/learn/<topic>/<lesson-slug>.ts` |
| Engine (do not fork per lesson) | `src/lib/walkthrough/` (`types.ts`, `schema.ts`, `helpers.ts`, `layout.ts` (floor layout), `stage.ts` (keyed animation core), `iso-stage.ts` (3D renderer), `player.ts`) |

No frontmatter field is needed: the page picks up the walkthrough whose path matches its slug. The `id` inside the file must equal its path without `.ts` (for example `problems/two-sum`). Every walkthrough also gets a standalone page at `/embed/<id>/`.

### Authoring

- Start with `export default defineWalkthrough({...})` and build scenes with the helpers: `arr`, `ptr`, `range`, `map`, `vars`, `note`, `link`, `tones`, `span`.
- Each step holds a **complete scene**. Keep entity ids stable between steps (`nums`, `idx`, `seen`...) so the renderer animates moves and colour changes instead of re-drawing.
- Write a small `scene(state)` builder function when steps share a layout (see `binary-search.ts`).
- 6–12 story steps. Each step has `short` (1–2 words for the rail), `title`, and `body` (max ~3 sentences; supports `**bold**` and `` `code` `` only).
- `code` holds the same Python solution shown on the page; steps highlight 1-based lines via `code: 5` or `code: [4, 5]`. The code panel shows line numbers and the step header shows a "Lines …" chip, so:
  - **Every step that runs code must set `code`**, listing exactly the lines that execute in that step (include the comment line when the step explains it).
  - The narration should name the lines it talks about ("Line 5 asks…"). Steps about ideas that aren't in the solution (e.g. brute force) leave `code` unset and say so.
- End the story on the step that explains the key decision in **your** solution (e.g. Two Sum ends on "check before store", the comment on line 7); put the complexity recap just before it.
- Use `metrics` for 2–4 live counters (lookups, checks, window size, answer) and `goals` to link "You'll learn" items to steps.
- Add a `trace` block when users should run the algorithm on their own input: `run(values)` executes the algorithm and returns generated steps. Reuse the same scene builder as the story so both modes look identical, and give generated steps the same `code` lines.
- Walkthroughs render **only in isometric 3D**. Scenes are authored in flat "floor" coordinates (x right, y down) and projected: cells become blocks (the `active`/`found` ones lift up), pointers become pins, links become arcs with moving packets, and `map`/`vars` tables and notes stand up as cards centred on their floor footprint. Keep tables at least ~100px away from arrays and put notes in open floor space, then check the result in the browser.
- The "You'll learn" goals point at story steps, so they are hidden in "Try your own" mode.

### Tone meanings (keep consistent)

| Tone | Meaning |
|------|---------|
| `active` | the element being processed right now |
| `compare` | being compared / current search window |
| `done` | already processed or stored |
| `found` | answer / match |
| `miss` | failed check, bug, or wrong path |
| `muted` | ruled out, no longer relevant |
| `note` | callout boxes |

### Validation

Walkthroughs are validated with Zod during `astro dev` / `astro build` (`src/lib/walkthrough/schema.ts`): unknown fields, duplicate ids, pointers out of bounds, links to missing keys, code lines past the end, unknown metrics, and trace runs that crash all fail the build. Run `pnpm check` and `pnpm build` before committing.

## 📊 Archify Diagram Rules

### When to Use Archify

| Use Case | Mode |
|----------|------|
| "Which algorithm should I use?" decision flow | `workflow` |
| Internal structure of a data structure | `architecture` |
| Step-by-step algorithm execution | ❌ use a **Walkthrough** instead (see above) |
| Concept hierarchy or comparison tree | `tree` |
| Data pipeline or solution data flow | `dataflow` |

### Required Settings

- Store candidates in `.archify/<type>-<slug>-<timestamp>/`
- Store final HTML in `public/diagrams/<topic>/<slug>.html`
- Use `--quality showcase` for all diagrams
- Use the **`classic`** visual preset consistently across all diagrams (omit `meta.visual_preset` or set `"classic"`, never mix presets)

## 🐍 Python Code Standards

- **PEP 8** compliant (4 spaces, snake_case, 79 char lines)
- **Type hints** on function signatures
- **Docstrings** not required (comments are preferred for brevity)
- Comments explain **why**, not **what**
- Prefer **built-in functions** over manual implementations
- Keep functions **under 30 lines**
- Use **descriptive variable names** (not `i`, `j` for non-indices)

---

## 🚫 Don'ts

- ❌ Don't write walls of text — use visuals
- ❌ Don't use academic/formal language — be friendly
- ❌ Don't create components without Claymorphism tokens
- ❌ Don't skip frontmatter fields — all are required
- ❌ Don't mix visual presets in Archify diagrams
- ❌ Don't create visualizers without playback controls
- ❌ Don't add algorithms without at least the markdown lesson
- ❌ Don't use inline styles — use CSS classes and custom properties
