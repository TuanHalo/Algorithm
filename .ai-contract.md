# 🤖 AI Contract — Algorithm Hub

> This file defines the rules and standards that any AI assistant (Antigravity, Copilot, etc.)
> **must follow** when contributing to this repository. Read this file before making any changes.

---

## 📌 Core Principles

1. **Friendly language** — Write like explaining to a friend, not a textbook. No academic jargon.
2. **Visuals over text** — Prefer diagrams, tables, badges, and interactive visualizations over long paragraphs.
3. **Consistency** — Every page, component, and diagram follows the established templates and design system.
4. **Interactive first** — Every algorithm lesson should include an interactive step-by-step visualizer.

## 📚 Algorithm Lesson Format (`src/content/learn/**/*.md`)

### Required Frontmatter

```yaml
---
title: "Algorithm Name"
topic: "topic-slug"        # sorting, searching, graph, etc.
order: 1                   # Display order within topic
difficulty: "beginner"     # beginner | intermediate | advanced
timeComplexity: "O(n²)"
spaceComplexity: "O(1)"
visualizer: "/visualizers/topic/algo-name.html"  # optional
diagram: "/diagrams/topic/algo-name-flow.html"   # optional
tags: ["tag1", "tag2"]
---
```

### Required Sections (in this order)

1. **🎯 What is [Algorithm]?** — 1-2 sentences. Use a real-life metaphor or analogy.
2. **🧠 Core Idea** — One-line summary in a blockquote. Example: `> Compare neighbors → Swap if wrong order → Repeat`
3. **🐍 Python Code** — Clean, commented implementation. PEP 8 compliant with type hints.
4. **⏱️ Complexity** — Table with Best / Average / Worst for both Time and Space.
5. **⚡ When to Use** — Two lines: ✅ Use when... / ❌ Avoid when...

> Note: The interactive visualizer (`visualizer:`) and Archify diagram (`diagram:`) declared in frontmatter are automatically rendered by `src/pages/learn/[topic]/[slug].astro` — do not leave empty HTML placeholder comments in Markdown.

### Writing Rules

- Maximum 2 sentences per explanation point
- Use emoji section headers (🎯, 🧠, 🐍, ⏱️, ⚡)
- Use tables instead of bullet lists for comparisons
- Code comments should explain **why**, not **what**
- Keep code under 30 lines (prefer concise implementations)

## 📝 Problem Solution Format (`src/content/problems/*.md`)

### Required Frontmatter

```yaml
---
title: "Problem Name"
platform: "leetcode"       # leetcode | hackerrank | codeforces | other
problemUrl: "https://..."
difficulty: "easy"         # easy | medium | hard
topics: ["hashing", "array"]
dateCompleted: "2024-01-15"
timeComplexity: "O(n)"
spaceComplexity: "O(n)"
diagram: "/diagrams/problems/problem-slug-flow.html"  # optional
---
```

### Required Sections (in this order)

1. **🔗 Problem** — 2-3 sentence problem description (not the full statement, just the gist)
2. **💡 My Approach** — 2-3 sentences explaining the thought process
3. **🐍 My Solution** — The submitted Python code with inline comments
4. **🤖 AI Feedback** — Four subsections:
   - **✅ Strengths** — What the solution does well (2-4 bullet points)
   - **🔧 Improvements** — What could be better (2-4 bullet points)
   - **🧪 Edge Cases** — Edge cases to consider (2-3 bullet points)
   - **🔄 Alternative Approaches** — Other ways to solve it (1-2 approaches with brief explanation)

> Note: When `diagram:` is set in frontmatter, `src/pages/problems/[slug].astro` automatically renders the **🎨 Visual Walkthrough** Archify diagram panel below the markdown body.

### Feedback Guidelines

When providing AI feedback on user's code:
- Be **encouraging first** — always start with genuine strengths
- Be **specific** — don't say "could be better", say exactly what and how
- Suggest **Pythonic** improvements (list comprehensions, built-ins, etc.)
- Mention **time/space tradeoffs** when suggesting alternatives
- Keep tone **friendly and supportive** — this is a learning journal, not a code review

## 🎬 Interactive Visualizer Rules

### Architecture

- All visualizers are **self-contained HTML files** in `visualizers/<topic>/`
- Use the shared engine: `visualizers/shared/visualizer-base.js`
- Use Claymorphism styles: `visualizers/shared/clay-visualizer.css`

### Required Features

Every visualizer must have:
1. **Input field** — User can enter custom data (e.g., array, graph)
2. **Step recording** — Algorithm records every comparison, swap, or operation
3. **Playback controls** — Play, Pause, Step Forward, Step Back, Speed slider
4. **Visual state** — Animated representation (bars, nodes, etc.)
5. **Code highlight** — Show the Python code alongside, highlight current line

### Styling

- Use Claymorphism design tokens (match the main site look)
- Pastel topic colors for highlighting active/compared elements
- Smooth CSS transitions (200-400ms)
- Responsive layout (works at 320px–1920px)

## 📊 Archify Diagram Rules

### When to Use Archify

| Use Case | Mode |
|----------|------|
| "Which algorithm should I use?" decision flow | `workflow` |
| Internal structure of a data structure | `architecture` |
| Step-by-step algorithm execution | `sequence` |
| Concept hierarchy or comparison tree | `tree` |
| Data pipeline or solution data flow | `dataflow` |

### Required Settings

- Store candidates in `.archify/<type>-<slug>-<timestamp>/`
- Store final HTML in `public/diagrams/<topic>/<slug>.html`
- Use `--quality showcase` for all diagrams
- Use the **`classic`** visual preset consistently across all diagrams (omit `meta.visual_preset` or set `"classic"`, never mix presets)

## 🐍 Python Code Standards

- **PEP 8** compliant (4 spaces, snake_case, 79 char lines)
- **Type hints** on function signatures
- **Docstrings** not required (comments are preferred for brevity)
- Comments explain **why**, not **what**
- Prefer **built-in functions** over manual implementations
- Keep functions **under 30 lines**
- Use **descriptive variable names** (not `i`, `j` for non-indices)

---

## 🚫 Don'ts

- ❌ Don't write walls of text — use visuals
- ❌ Don't use academic/formal language — be friendly
- ❌ Don't create components without Claymorphism tokens
- ❌ Don't skip frontmatter fields — all are required
- ❌ Don't mix visual presets in Archify diagrams
- ❌ Don't create visualizers without playback controls
- ❌ Don't add algorithms without at least the markdown lesson
- ❌ Don't use inline styles — use CSS classes and custom properties
